# AI 研发知识库 · 可运行示例

一个目录里放下三层知识、三套 Skill，和一个已经接好的工作区。`git clone` 之后用 IDE 打开本目录下的 `workspace/` 就能用，不需要安装、不需要脚本、不需要凭据。

配套文章：[《AI 研发知识库构建思路》](https://mp.weixin.qq.com/s/qzb42qlI7Fwvzj4v0UD2Kg) · 《AI 研发知识库落地拆解》（本篇）

> 请用 `git clone`，不要用 Download ZIP —— ZIP 包不保证保留软链。

## 目录

| 目录 | 是什么 | 谁担保 |
| --- | --- | --- |
| `drafts/knowledge/` | 知识草稿，会话里刚冒出来的判断 | 无人 |
| `group/knowledge/` | 团队知识，本组验证过的条目 | 本组负责人 |
| `knowledge-base/knowledge/` | 公共知识包，跨组通用 | 架构评审 |
| `drafts/skills/`、`group/skills/`、`knowledge-base/skills/` | 三套 Skill，各有来处 | 各自维护方 |
| `workspace/` | 业务工作区，IDE 打开这里 | — |

## 运行时：注入、挂载、读取、命中

前面讲的是知识怎么进库；这一节讲 AI 开工后怎么把它用上。`workspace/README.md` 软链指回本文件，下面就是这个工作区实际的入口规则。

### 1. 工作区起来时，注入什么

生成工作区只做两件事：把三套 Skill 汇到 `.agents/skills/`，把两层知识挂成软链。五条注入各有来处，不是一起塞进来的：

| 注入项 | 从哪来 | 什么条件下出现 |
| --- | --- | --- |
| 草稿捕获 Skill | `drafts/skills/` | 默认就有，不需要配置 |
| 工作组 Skill | `group/skills/` | 本组声明启用、本组维护 |
| 随包 Skill | `knowledge-base/skills/` | 声明引用知识包时才注入 |
| `knowledge` 软链 → `group/knowledge/` | 团队知识 | 本组知识，可写，随时沉淀 |
| `knowledge-base` 软链 → `knowledge-base/knowledge/` | 公共知识包 | 引用包时才有，按约定只读 |

**引用知识包是成对的**：声明了包，才既注入随包 Skill、又挂上只读软链。少一半，AI 就会按旧判据往新目录送候选，或者读得到知识却不知道该怎么贡献。

`workspace/` 里除 `code/` 外全是相对软链，知识本体从不复制进项目：一处更新，接入的工作区立即看到新版；项目归档也不会把团队知识打包带走。三套精简 Skill 各写「知识怎么进、运行时怎么被用」两个流程，见各自来源目录的 SKILL.md。

### 2. 两条流程在 Skill 里

三套 SKILL.md 每套只有两个流程：**流程一**是这一层知识怎么进，**流程二**是运行时这一层怎么被用。三套合起来就是完整链路：草稿层不读 → 先扫团队索引、读正文、按首查入口定死第一步 → 需要跨组背景才查公共索引 → 命中后对不上就地更新那一层（公共层走评审）→ 作废须指向替代条目。`pending/` 候选不进检索。规则与知识同版本，不另在 README 里重复一遍。

### 3. 跟着跑一遍

用上篇第二次报障的原话当输入，在全新会话里说一句「配置项的条件时对时不对」：

| 步 | 读什么 | 得到什么 | 下一步 |
| --- | --- | --- | --- |
| 1 | 任务描述 | 现象是条件时对时不对，位置像配置读取 | 不从前端渲染开始绕 |
| 2 | `knowledge/index/documents.json` | 命中《同名配置项返回多条的排查手册》 | 打开 `runbooks/` 正文 |
| 3 | 条目的「首查入口」 | 记下组件名和重复项名，对照两张配置表 | 第一步被定死 |
| 4 | 当前代码与数据 | 确认新旧两套配置是否并存 | 用「核心判断」解释现象 |
| 5 | 「修复约束」 | 先定权威配置，再清理遗留套 | 只改其中一处无效 |
| 6 | `pending/配置优先级与覆盖规则.md` | 仍是待审候选，**不参与默认检索** | 不当定论引用 |

第 6 步就是排除验证：长得像但不该用的知识，必须读不到。

## 一条知识走完全程

同一条判断在本示例里有三个形态，核心结论始终是「同一组件的配置存在新旧两套，先定权威配置再去重」：

| 位置 | 形态 | 担保 |
| --- | --- | --- |
| `drafts/knowledge/20261110-同名配置/draft.md` | 会话碎片 | 无 |
| `group/knowledge/runbooks/同名配置项返回多条.md` | 五段骨架的正式手册 | 本组 |
| `knowledge-base/knowledge/pending/配置优先级与覆盖规则.md` | 剥离项目后的通用机制，待评审 | 待跨组评审 |

晋升就是换担保人，不是重写一条。

## 怎么验

- **软链**：`git ls-files -s` 里软链应是 `120000`；`cat workspace/knowledge/catalog.md` 能读到内容。
- **命中**：全新会话里说「配置项的条件时对时不对」，看是否查到那条手册、第一步是否指向对照两张配置表。
- **排除**：跑几个不相关任务，看会不会把这条硬套上去。
- **生效**：改一条结论再跑旧场景，看用的是新答案；把条目标作废，看还会不会被引出来。

`workspace/code/` 是放项目代码的位置，示例不预置内容；命中验证只需一句现象描述，不需要跑代码。

## 说明

本示例是最小实现，只放一条知识、三套精简 Skill（每套两个流程）；目录结构保持完整，便于替换成自己的工程。
